# Codee v2.1.5 Trust-Boundary Hardening

This release hardens three boundaries before wider provider/autonomy work.

## 1. Verified Artifact Receipt

New plans saved by v2.1.5 set `artifactVerificationMode: receipt_required`.
A valid `CODEE_ARTIFACT` footer is necessary but not sufficient for advancement.
Codee must receive a host-generated artifact receipt proving the actual ZIP bytes exist and match the footer.

The host is supplied as `globalThis.CodeeArtifactVerificationHost` (or a repository host exposing the same `verifyArtifact` method):

```js
await CodeeArtifactVerificationHost.verifyArtifact({
  artifact: { artifactId, zip, sha256, zipSize, version },
  context: { tabId, planId, runId, stepId, stepToken, stepCompleted }
})
```

The returned receipt must include:

- `verified: true`
- `receiptId` / `id`
- `exists: true`
- `downloadComplete: true`
- exact `zip` filename
- a non-empty local `path` / `artifactPath`
- `actualSha256` matching the footer SHA-256
- `actualSize` matching `ZIP_SIZE` when supplied
- `zipIntegrity: PASS`
- `verifiedAt`

If the verifier is unavailable or any receipt field fails validation, the plan does not advance. It remains recoverable and Diagnostics reports the missing/failed byte-verification reason.

Plans created by older Codee versions remain footer-only for compatibility; new v2.1.5 plans are receipt-required.

## 2. Governed MCP Tool Gateway

`mcp.tool.call` no longer calls discovered tools directly.

Every tool must have a trusted classification from discovery metadata:

- `READ`
- `WRITE`
- `EXECUTE`
- `DESTRUCTIVE`

Supported metadata sources are `codeeClassification`/`classification` or MCP annotations such as `readOnlyHint` and `destructiveHint`. Unknown classification is denied.

`READ` tools may execute directly after argument/result sanitization.

All non-read tools require the MCP host to provide:

```text
prepareToolMutation
createToolBackup
verifyToolBackup
requestToolApproval
callTool
verifyToolMutation
auditToolMutation
```

The enforced order is:

```text
classify -> determine canonical targets -> backup -> verify backup -> approval -> execute -> verify result -> durable audit -> rollback receipt
```

No verified backup means no mutating MCP call.

MCP context gathering is stricter: tool-based context collection accepts READ tools only. Resources and prompts remain read-only evidence surfaces.

## 3. Provisional Conversation Identity

New ChatGPT/Claude pages without a structured conversation URL receive a page-session identity:

```text
chatgpt:page:new-chat:<uuid>
claude:page:new-chat:<uuid>
```

The content script persists the provisional ID in page `sessionStorage`, reports it to the service worker, and retains it while the provider transitions to a permanent conversation URL.

Once a permanent identity appears, Codee performs a one-way promotion:

```text
chatgpt:page:new-chat:<uuid> -> chatgpt:<conversation-id>
```

Orphan rebind supports exact provisional restoration and a unique provisional-to-structured promotion when the old tab is gone. Ambiguous matches remain fail-closed.

## Authority invariants

These changes do not alter Codee's authority model:

- Models/managers cannot advance plans.
- The Codee plan state machine remains the sole advancement authority.
- Repository and server writes remain backup-gated.
- The external MCP companion owns transport, not Codee's repository/workforce intelligence packs.
