# Public estimate token to company storage resolution

**Status: proposal only. No database schema, RLS policy, role grant, or token format was changed here.** This records the contract required before public estimate reads and responses can work after the web tier switches to `ai_fsm_web` and company-owned operational data is physically separated by company.

## Source findings

The current estimate portal token is a raw UUID. Migration `015_client_portal.sql:3-8` adds `estimates.share_token UUID NOT NULL DEFAULT gen_random_uuid() UNIQUE`; the column is indexed at lines42-45. There is no `token_hash` field or verification step for this token. The estimate send route builds `/portal/estimates/${est.share_token}` directly (`apps/web/app/api/v1/estimates/[id]/send/route.ts:45,147-158`), and other pages build links from the same stored value. The value is currently a bearer capability stored in plaintext.

The public estimate GET route reads the estimate by `share_token` before establishing any account context (`apps/web/app/api/portal/estimates/[token]/route.ts:46-61`). POST begins a tenant transaction and selects `id,status,account_id ... FOR UPDATE` by token at lines104-118, then sets `app.current_account_id` from the selected row at lines126-130. The selected row cannot supply context to a role that cannot select that row. The current policy is `estimates_select USING (account_id = app_account_id())` (`db/migrations/003_rls_policies.sql:247-249`), so a valid token returns no row to `ai_fsm_web` before the context statement can run. The expected-failure regression is in `response.unit.test.ts`; it preserves this ordering gap without adding a baseline failure.

The web DB module creates one process-global PostgreSQL pool from `DATABASE_URL` (`apps/web/lib/db.ts:9-17`). `packages/storage/src/index.ts:13-17,94-101` defines a `CompanyStorage` wrapper, but `forCompany` only wraps an already-open `StorageClient`; it does not resolve physical placement. I found no current company-to-database placement resolver in the web, storage, or platform paths searched. This matches #809's open requirement to route through a fail-closed Company Storage Resolver before dialect/client selection ([#809 implementation audit](https://github.com/Masterleeaus/Titan-Zero-Field-Service-Workforce/issues/809#issuecomment-5943002101)).

`company_id` is the canonical logical tenant identity; `account_id` remains compatibility schema (`db/MIGRATION-OWNERSHIP.md`). The RLS policy still consumes `account_id`, and the repository does not establish that a future canonical `company_id` is always byte-for-byte the same value. A trusted company-to-legacy-account binding is therefore required before setting that GUC; do not derive it from a request field or silently assume equality.

The RLS runbook already calls for a bounded `SECURITY DEFINER` pre-session lookup for portal tokens in the current shared-database model (`docs/working/rls-web-tier-flip.md:50-75`); `app_login_candidates` is a precedent with fixed `search_path`, revoked `PUBLIC` execute, and a narrow result (`db/migrations/178_runtime_login_boundary.sql:3-17`). Such a function inside one tenant database cannot locate which physical tenant database to open. A cross-company lookup must therefore operate only on approved control metadata, or the verified token itself must carry the signed company locator. It must never query or return estimate business data as a way around tenant RLS.

#648 sets the repository boundary: native Titan operational data is not moved into a shared Frappe database, `company_id` stays canonical, and new storage migrations need an explicit owner (`db/MIGRATION-OWNERSHIP.md`). #302's latest public draft PR #1183 (`4398dcf`) verifies authenticated, audience/company/actor/device-bound sessions; its registry contract explicitly stores no bearer credentials. That identity/session registry is not a public estimate capability registry. The external estimate customer remains anonymous and gets no Titan actor, user session, company role, or business authority from possessing a link.

The separate email approval token is an HS256 JWT with `estimateId` and `action`, signed for 30 days (`apps/web/app/api/v1/estimates/[id]/send/route.ts:20-26,147-157`). Its verifier checks those two claims (`apps/web/app/api/v1/estimates/[id]/respond/route.ts:56-65`), but it has no company claim or placement locator. It therefore cannot open a per-company database safely either. It is distinct from the raw `share_token` URL.

## Recommended contract and ownership

**Target integration owner: #809**, because it owns the full native `apps/web` product and explicitly requires a fail-closed Company Storage Resolver before dialect/client selection. The current storage package only exposes `forCompany(openStorage, companyId)`; it has no placement lookup or database-opening resolver. The resolver and its company placement record therefore remain an upstream canonical dependency, not something this portal route can safely invent. Canonical rules place company identity and storage placement in bounded control-plane/bootstrap ownership and say placement never grants authority; #648 coordinates that shared boundary and must approve the trusted `company_id` to legacy `account_id` binding before it is persisted or exposed. #302 should review public-token key/validation boundaries only. Its authenticated actor/session registry is not a public-link registry: do not add anonymous links there or edit its active session implementation.

Subject to agreement by #809/#648 and a bounded token-key review by #302, for newly issued links prefer a versioned, self-authenticating public capability so the web server can identify the company before opening operational storage, without scanning tenant databases or creating a shared business-data store. This is a proposed contract, not an existing Titan token API. The fixed token profile should bind:

- a dedicated token type, issuer, audience and key ID, with an algorithm allowlist configured at trusted startup;
- the canonical `company_id`, `estimate_id`, purpose (`estimate-view` or `estimate-response`), and an explicit expiry;
- a `jti`/link epoch tied to the estimate's current `share_token` value so a server-side rotation invalidates old tokens;
- for email approve/decline links, the specific action, preserving the current action binding.

Use a public-link signing key distinct from web session credentials, with fixed trusted algorithm/key configuration and rotation ownership agreed before implementation. The token is an anonymous bearer capability, never a session. After cutover, the raw UUID alone must no longer authorize access; only a valid signed envelope does. The current UUID can serve as a non-authorizing link epoch and be compared with the signed `jti` after the tenant context is established. If policy requires no bearer-derived value at rest, changing that epoch to a keyed digest requires an explicit migration and key-rotation design; no such requirement or hash currently exists in source.

The request path should be:

1. Verify token signature, type, issuer, audience, expiry, purpose, and required claims before accessing business storage. Invalid tokens fail with the same public `404` behavior and cause no tenant-storage lookup.
2. Pass only verified `company_id` to the canonical Company Storage Resolver consumed by #809. It returns an opaque handle for that company's physical database plus the trusted compatibility `account_id` binding required by current RLS. Missing, disabled, ambiguous, or inconsistent placement fails closed. The caller never provides a DSN, database name, `company_id`, or `account_id`; there is no global-pool fallback. This step is blocked until the canonical resolver and placement owner expose their interface; a portal-local resolver, token scan across tenant databases, or session-registry lookup is not a substitute.
3. Open the resolved tenant DB, begin a transaction, and set `app.current_account_id` from the resolver's trusted binding **before the first protected query**. Keep `ai_fsm_web` `NOSUPERUSER NOBYPASSRLS`; use existing tenant policies.
4. Select or lock only `WHERE id = verified.estimate_id AND account_id = resolved.account_id AND share_token = verified.jti`. For POST, retain the conditional `status = 'sent'` write and required transactional audit. GET uses the same context-first lookup and returns only the token-bound estimate. Do not attach estimate fields or an owner identity to the pre-open resolver result.

This does not need a cross-tenant `SECURITY DEFINER` function for estimate business rows. If an owner chooses a central legacy-token locator instead, that is separate control metadata: it may return only a bounded company/resource pointer from a token fingerprint, must expose only a narrow function to the runtime role, and still must open the resolved tenant DB and apply RLS context before reading business data.

## Decisions required before implementation

1. **Existing links:** current raw UUID links have no signed company claim. Choose whether the per-company rollout will rotate/reissue these links or temporarily resolve them through a bounded token-fingerprint directory. Signed v2 tokens cannot preserve old raw links by themselves. A directory would be shared security-sensitive control metadata and needs an explicit #648 placement/retention owner.
2. **Tenant binding:** define the authoritative `company_id` → legacy `account_id` mapping consumed by RLS. Confirm equality only if the migration/provisioning data proves it for every company; otherwise put the binding in the trusted company placement registry.
3. **Expiry/revocation:** decide whether `estimates.expires_at` expires the public link or only the quote, and how long view and response links remain valid. The current public POST does not select or enforce `expires_at`; do not silently change customer behavior while changing routing.
4. **Token-at-rest:** decide whether the existing random UUID may remain as a non-authorizing epoch after all routes require the signature, or whether a versioned hash column is required. Hashing would require coordinated link issuance, backfill/rotation, and rollback rules.

## Minimal implementation and test boundary

After those decisions, #809 owns the Company Storage Resolver integration and the estimate link issuer/consumer paths: the public estimate server page, GET/POST route, estimate-send link generation, existing authenticated copy/share-link generation, and email responder/landing page. Keep the initial change to estimate links; the invoice/client portal, Square webhook and other sessionless entries from TASK-146 need their own inventory and tests before enabling the restricted role globally.

Required tests should run the route against a real `NOSUPERUSER NOBYPASSRLS` role and exercise two physically separate company databases. Assert the verified company is resolved before any business DB opens; account context is set before the first estimate read; the valid link reads/responds only in its company; the same estimate ID in another company is unchanged; cross-company substitution, invalid signature, unknown/revoked/expired epoch and unavailable placement fail closed without writes. Also prove database lookup errors or audit failure do not commit a response. No broad policy, token-search fanout, cross-company query, or synthetic owner session belongs in the fix.

## #1149 email-audit handoff

The fail-open writer is in the **web** route `apps/web/app/api/v1/estimates/[id]/respond/route.ts`, not worker code. After the status update (`:75-85`), lines91-110 run the nullable `audit_log` insert (`actor_id NULL`) in `Promise.all` with `writeWorkflowEvent`, then catch every rejection and only log `estimate respond: audit/event writes failed`. The handler proceeds through attention/artifact work and commits at line193. Audit failure therefore does not roll back the approved/declined status. The other promise can also fail under the same catch, so current logging does not distinguish missing audit from missing workflow event. This is a web-owned transactional evidence follow-up; no worker files were edited.
